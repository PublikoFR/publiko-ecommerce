# pko/lunar-loyalty — fidélité B2B

Portage du module PrestaShop `publikoloyalty` (v1.1.0) vers Lunar. Phase 1 : back-office uniquement, storefront différé.

### Décisions
- **Package** : `packages/pko/loyalty`, namespace `Pko\Loyalty\`, ServiceProvider `LoyaltyServiceProvider` (enregistré dans `bootstrap/providers.php`).
- **Plugin Filament** : `LoyaltyPlugin` enregistré dans `AppServiceProvider` après `CatalogFeaturesPlugin`. Resources : `LoyaltyTier` (CRUD), `GiftHistory` (statut + notes + badge nav unviewed), `PointsHistory` (readonly). Page `LoyaltySettings` (ratio + email admin). Group nav : **Marketing**.
- **Trigger calcul points** : observer Eloquent sur `Lunar\Models\Order` (`updated`/`created`), déclenché quand `placed_at` passe à non-null. Choix vs `PaymentAttemptEvent` : robuste pour les paiements offline et idempotent (vérification d'existence dans `pko_loyalty_points_history.order_id` unique).
- **Source HT** : colonne `lunar_orders.sub_total` (entier cents, hors taxes). `points = floor((sub_total/100) / ratio)`.
- **Anti-doublon palier** : index unique `(customer_id, tier_id)` sur `pko_loyalty_gift_history`.
- **Déblocage multi-paliers** : `unlockEligibleTiers()` débloque **tous** les paliers éligibles (points_required <= solde) sans GiftHistory, pas seulement le plus haut atteint. Sans ça, un palier ajouté après coup sous le solde déjà acquis d'un client (ou un saut de plusieurs paliers en une seule commande) reste invisible pour toujours : ni « à venir » (déjà dépassé), ni « débloqué » (jamais inscrit en base). Commande `php artisan loyalty:recalculate` (`--dry-run` pour compter sans écrire) pour rattraper les clients déjà existants — idempotente, ne crée que les GiftHistory manquantes.
- **Notifications** : client via `TierUnlockedMail` (`TemplatedMail`, clé `loyalty.tier_unlocked`). Équipe via `TierUnlockedAdminMail` (clé `loyalty.tier_unlocked_admin`, audience équipe) envoyé par `AdminRecipient::send()` à `admin_notification_email()` (Storefront → Paramètres). Repli env `LOYALTY_ADMIN_EMAIL`. Le champ e-mail admin n'est plus dans Fidélité.
- **Settings** : table dédiée `pko_loyalty_settings(key, value)` — pas de dépendance `spatie/laravel-settings` ajoutée. Lecture via `Pko\Loyalty\Models\Setting::get()`.
- **Cadeau typé (plus de cadeau libre)** — migration `2026_11_10_000000_add_gift_type_to_pko_loyalty_tiers`. Chaque palier a un `gift_type` (enum `GiftType`) : `voucher` (bon d'achat, `voucher_amount`), `franco` (franco de port abaissé, `franco_threshold`), `bfa` (`bfa_fixed_amount` + `bfa_percent`, décimal 5,2). Tous les montants sont **HT, en cents** ; le formulaire admin les saisit en euros (`formatStateUsing`/`dehydrateStateUsing` × 100) et n'affiche que les champs du type choisi (`->live()`). Les champs d'un autre type sont remis à null à l'enregistrement (`LoyaltyTierResource::clearOtherTypeFields()`, appelé par les pages Create/Edit) : un palier passé de bon d'achat à BFA ne garde pas un montant fantôme. Intitulé affiché partout (admin, espace client, e-mails) : `LoyaltyTier::giftLabel()` (« Bon d'achat de 50 € HT », « Franco de port dès 300 € HT », « BFA : 100 € HT + 2 % »).
  - `gift_title`, `gift_description` et la photo (`pko_mediables`, mediagroup `gift_image`) sont **supprimés** (colonnes droppées, rattachements effacés, `HasMediaAttachments` retiré du modèle). Reprise : un intitulé « Bon d'achat 50€ » devient `voucher` 5 000 cents ; tout autre palier passe en `voucher` **sans montant** → aucun bon émis tant que l'admin ne l'a pas renseigné (log warning).
  - **Le palier `bfa` est calculé et versé ici** (cf. « BFA »), le franco est actif (cf. « Franco abaissé »).
- **Bon d'achat automatique (palier `voucher`)** — `LoyaltyVoucherService::issueFor(GiftHistory)`, appelé par `unlockEligibleTiers()` pour chaque **nouveau** déblocage d'un palier voucher. Un bon = une remise Lunar :
  - type `Pko\Loyalty\DiscountTypes\LoyaltyVoucher` (montant HT en cents dans `data.voucher_amount`), code unique `FID-XXXXXXXX` (caractères ambigus 0/O/1/I/L exclus), `max_uses = 1`, réservé au client (`lunar_customer_discount`), `starts_at` = déblocage, `ends_at` = +60 jours (`VALIDITY_DAYS`), handle `loyalty-voucher-<gift_history_id>`, `priority = 0` (appliqué après les autres remises), activé sur tous les canaux et **tous** les groupes clients (les hooks Lunar n'activent que ceux par défaut ; un client B2B est rarement dans le groupe par défaut).
  - **Pourquoi un type dédié et pas `AmountOff`** : `AmountOff` à montant fixe ne s'applique pas du tout si le panier est inférieur au montant. `LoyaltyVoucher` s'applique plafonné au HT du panier, **le reste est perdu** (usage unique). Il **ajoute** sa remise à celles déjà posées sur les lignes (pas de « meilleure des deux ») : le bon fidélité se cumule toujours.
  - **Identifier un bon fidélité** (règle de non-cumul des remises) : `LoyaltyVoucher::isLoyaltyVoucher($discount)` (= `$discount->type === LoyaltyVoucher::class`). Handle préfixé `loyalty-voucher-` en second repère.
  - **Cumul avec la remise client %** : `LoyaltyServiceProvider::boot()` ajoute `LoyaltyVoucher` à `config('customer-auth.stackable_discount_types')` ; `CartDiscountArbiter` (customer-auth) applique alors le bon après l'avantage retenu (remise client ou promotion), sans l'inclure dans la comparaison (cf. `docs/packages/customer-auth.md`, « Non-cumul »).
  - **Validation du code au panier** : le `CouponValidator` de Lunar ne connaît que `AmountOff`/`BuyXGetY`. `LoyaltyServiceProvider` lie `Lunar\Base\Validation\CouponValidator` à `LoyaltyCouponValidator` (accepte aussi les bons fidélité actifs et non utilisés) — `config/lunar/discounts.php` reste intact. Si un autre validateur est un jour configuré dans ce fichier, il doit déléguer au nôtre.
  - Le type n'est **pas** enregistré via `Discounts::addType()` : il n'apparaît pas dans la liste des types créables dans l'admin Lunar (un bon fidélité n'a de sens qu'émis par le programme). Les bons restent visibles et désactivables dans Ventes → Remises.
  - **Idempotence** : `gift_history.discount_id` unique + verrou (`lockForUpdate`) sur le déblocage ; un second appel renvoie le bon existant. Un seul bon par déblocage.
  - **Pas de rétroactivité** : seul un déblocage créé par `unlockEligibleTiers()` émet un bon. Les GiftHistory antérieures restent sans bon, `loyalty:recalculate` n'en émet que pour les déblocages qu'il crée.
  - **E-mail** : `LoyaltyVoucherMail` (`ShouldQueue`, clé `loyalty.voucher_issued`, template neutre : code, montant HT, date d'expiration, lien vers l'espace fidélité). Pour un palier voucher il **remplace** `TierUnlockedMail` côté client (un seul message par déblocage) ; l'e-mail équipe `loyalty.tier_unlocked_admin` part inchangé. `email_sent` passe à true à la mise en file.
  - **Espace fidélité** : la liste « Suivi de vos cadeaux débloqués » affiche pour un bon le code (sélectionnable), le montant HT, la date d'expiration et le statut (`GiftHistory::voucher()` → Valable / Utilisé / Expiré / Annulé, calculé depuis la remise Lunar : `uses`, `ends_at`, `data.disabled_at`). Admin : colonne « Bon d'achat » (code copiable + statut) dans l'historique des cadeaux et sur la fiche client.
  - **Remboursement** (`revokeForRefunds`) qui fait repasser le solde sous un palier voucher de l'année : bon **non utilisé** → désactivé (`ends_at = now`, `data.disabled_at`) et déblocage supprimé, quel que soit son statut (le palier redevient débloquable si le client regagne les points) ; bon **déjà utilisé** → déblocage gardé (cadeau consommé). Les autres types gardent la règle existante (seul un cadeau `pending` est supprimé).
- **Franco abaissé (palier `franco`)** — au déblocage, le client bénéficie d'un seuil de franco personnel (`franco_threshold`, cents HT), valable jusqu'au 31/12 de l'année du déblocage. Pas d'émission ni d'e-mail dédié : l'avantage **est** la ligne `GiftHistory` de l'année en cours (e-mail générique de palier).
  - **Lecture** : `Pko\Loyalty\Services\LoyaltyFrancoThreshold` implémente le contrat `Pko\ShippingCommon\Contracts\CustomerFrancoThresholdProvider` ; `LoyaltyServiceProvider` le lie **seulement si** l'interface existe (dépendance optionnelle vers pko/shipping-common, non déclarée dans `require`). Seuil = **minimum** des `franco_threshold` des paliers franco débloqués **cette année** (plusieurs paliers franco → le plus bas). Le palier n'a pas à être encore actif : un avantage acquis le reste jusqu'au 31/12.
  - **Client du panier** : `cart.customer_id`, sinon les clients rattachés à `cart.user_id`.
  - **Fin d'année** : `gift_history.year` ≠ année courante → plus pris en compte, en même temps que la remise à zéro des points.
  - **Remboursement** : `revokeForRefunds` supprime le déblocage franco quel que soit son statut dès que le solde repasse sous le palier (le seuil personnel disparaît aussitôt).
  - **Effet sur le port** : cf. `docs/shipping.md` §5.10 (seuil effectif = min(global, personnel) ; forfaits `pko_transport_price_cents` toujours facturés).
  - **Affichage** : espace fidélité (bloc « Livraison standard offerte dès X € HT », valable jusqu'au 31/12 ; dans le suivi des cadeaux, badge Actif/Expiré au lieu du statut d'envoi), panier (« Livraison offerte dès X € HT · avantage fidélité ») et bandeau de progression du checkout. `getCustomerSnapshot()` expose `franco_threshold`.
- **BFA — bonus de fin d'année (palier `bfa`)** — migration `2026_11_11_000000_create_pko_loyalty_bfa_payouts_table`.
  - **Tranches** (`BfaCalculator::tranches(customerId, year)`) : chaque déblocage d'un palier BFA (`GiftHistory` de l'année) ouvre une tranche, close au déblocage du palier BFA suivant du même client ou au 31/12. Valeur d'une tranche = `bfa_fixed_amount + bfa_percent % × CA de la tranche` ; les tranches **se cumulent** (un client qui passe Argent puis Or touche le fixe + % d'Argent sur son CA entre les deux, puis celui d'Or jusqu'au 31/12).
  - **CA** = même base que les points : `points_history.order_total_ht` (HT hors port), **net des remboursements** au prorata (Σ remboursé TTC / total TTC, comme `revokeForRefunds`). Remboursement intégral → 0. Les commandes d'une autre année ne comptent pas.
  - **Commande qui débloque un palier** : passée avant le déblocage, elle compte dans la **tranche précédente** (ou nulle part si c'est le premier palier BFA), jamais dans celle qu'elle ouvre. Affectation par `gift_history.order_id`, pas par horodatage (même seconde). Un saut de deux paliers BFA en une commande ouvre une tranche vide (fixe seul) puis la suivante.
  - Arithmétique **entière** (`percentOf` en points de base, `roundDiv`) : aucun float sur un montant.
  - **Déblocage annulé** par un remboursement (cadeau `pending` supprimé par `revokeForRefunds`) → la tranche disparaît ; son brouillon de versement est purgé au pré-calcul suivant. Un avoir déjà émis n'est jamais touché.
  - **Espace fidélité** : `getCustomerSnapshot()['bfa']` = `{year, acquired, tranches}` (null sans palier BFA débloqué cette année). Carte « BFA acquis à ce jour : X € HT — versé en janvier N+1, sous forme d'avoir », détail par tranche (CA de la période + montant). Estimation recalculée à chaque affichage, pas de stockage.
  - **Table `pko_loyalty_bfa_payouts`** : une ligne par tranche (`gift_history_id` unique, `nullOnDelete` pour qu'un avoir émis survive à son déblocage). Instantané du calcul (`period_start/end`, `revenue_ht`, `fixed_amount`, `percent`, `computed_amount`), `adjusted_amount` (saisie admin, prime sur le calcul), `status` (`draft` → `issuing` → `issued` | `failed`), `external_reference` unique `bfa_<année>_<gift_history_id>`, `pennylane_id`, `credit_note_number`, `last_error`, `issued_at`.
  - **Admin : Marketing → BFA de fin d'année** (`Pko\Loyalty\Filament\Pages\BfaPayouts`, slug `fidelite/bfa`). Filtre année (défaut : année écoulée) et statut. « Pré-calculer » (`BfaCalculator::precompute`) crée/met à jour une ligne par tranche — idempotent, garde l'ajustement admin, ne modifie jamais une ligne émise, en cours ou ayant déjà un document distant (`pennylane_id`). La purge des tranches disparues ne touche que les brouillons purs (`draft` sans `pennylane_id`) : une ligne `failed` garde sa trace d'erreur. Action « Ajuster » (euros HT, virgule acceptée ; saisir le montant calculé efface l'ajustement), visible seulement si `BfaPayout::isAmountEditable()` (modifiable **et** aucun document distant) : dès que l'avoir existe chez Pennylane, même en brouillon après une finalisation refusée, le montant est gelé. « Émettre les avoirs » (toute l'année), « Émettre l'avoir » (ligne) et action groupée.
  - **Émission** (`BfaPayoutEmitter`) : refusée tant que l'année n'est pas close (`canIssueYear` : année < année courante — une tranche court jusqu'au 31/12) et pour un montant nul (ligne ignorée, reste `draft`). Ligne réservée par une mise à jour conditionnelle (`draft|failed` → `issuing`) : deux clics simultanés n'émettent qu'une fois. Réservation plus vieille que 10 min (`ISSUING_STALE_MINUTES`) = plantage, reprise possible. Échec → `failed` + `last_error` (infobulle du statut), ré-émissible.
  - **Découplage comptable** : contrat `Pko\Loyalty\Contracts\BfaCreditNoteIssuer` ; défaut `NullBfaCreditNoteIssuer` (refuse, `bindIf`) remplacé par `pko/pennylane` (`LoyaltyBfaCreditNoteIssuer`, cf. docs/packages/pennylane.md). Le package loyalty ne dépend pas de Pennylane.
  - TVA de l'avoir : `LOYALTY_BFA_VAT_RATE` (défaut 20) — une remise de fin d'année réduit la base taxable des ventes.
- **Ordre des paliers** : champ `position` retiré du formulaire admin. Le glisser-déposer (`->reorderable('position', false)`) est désactivé côté UI mais **pas supprimé du code** (économie de compute, réactivable en repassant `true`) — la liste est triée par `points_required` croissant (`->defaultSort('points_required')`), colonne déjà `->sortable()`.

- **Cycle annuel (remise à zéro au 1er janvier)** : `customer_points.points_year` rattache le solde à une année civile. Un solde d'une année passée vaut 0. Double mécanisme : `LoyaltyManager::ensureCurrentYear()` remet à zéro à la volée avant toute écriture (gain ou retrait), et la commande `loyalty:reset-annual` (planifiée **chaque jour** à 00:05, pas `yearlyOn(1, 1)` : rattrape un scheduler arrêté le 1er janvier, no-op le reste de l'année) remet à zéro en base pour que l'admin affiche aussi 0. `getCustomerSnapshot()` renvoie 0 pour un solde d'année passée même si la commande n'est pas encore passée.
- **Paliers re-débloquables chaque année** : `gift_history.year`, unicité `(customer_id, tier_id, year)` (avant : `(customer_id, tier_id)`). Le snapshot expose `unlocked_tiers` = année en cours (piste Flow) et `gift_history` = tout l'historique (liste « Suivi de vos cadeaux »).
- **Retrait de points sur remboursement / avoir** : observer `RefundTransactionObserver` sur `Lunar\Models\Transaction` (`saved`, `type=refund`, `success=true`). Les avoirs Pennylane naissent de ces mêmes transactions (`TransactionPennylaneObserver`) → un seul point d'entrée. `revokeForRefunds()` retire **au prorata** : `cible = round(points_earned × Σ remboursé TTC / total TTC)`, plafonnée à `points_earned`, stockée dans `points_history.points_revoked` ; seul l'écart avec la cible précédente est retiré (idempotent, remboursements partiels successifs gérés). Solde plancher 0, `current_tier_id` recalculé. Si le solde repasse sous un palier débloqué **cette année**, le cadeau encore `pending` est supprimé ; `processing`/`sent` conservé. Remboursement d'une commande dont les points ont été gagnés une année passée → ignoré (points déjà remis à zéro). Pas de statut Lunar « annulée » configuré : une annulation passe par un remboursement.

### Tables (préfixe `pko_loyalty_`)
- `pko_loyalty_tiers` — paliers (name, points_required, gift_type, voucher_amount, franco_threshold, bfa_fixed_amount, bfa_percent, position, active)
- `pko_loyalty_customer_points` — agrégat par client (unique customer_id)
- `pko_loyalty_points_history` — trace par commande (unique order_id → idempotence)
- `pko_loyalty_gift_history` — déblocages (status enum pending/processing/sent, admin_notes, admin_viewed, `discount_id` unique → bon d'achat Lunar émis)
- `pko_loyalty_settings` — kv config
- `pko_loyalty_bfa_payouts` — versements de BFA par tranche (montant calculé/ajusté, statut d'émission, n° d'avoir)

### Storefront — page fidélité client (`account.loyalty`)
- Livewire `Pko\Account\Livewire\LoyaltyPage` (package `account`), vue `account::livewire.loyalty-page`.
- Données via `LoyaltyManager::getCustomerSnapshot(int $customerId)` — signature **int**, passer `$customer->id` (pas l'objet `Customer`, sinon `TypeError` sous `strict_types` → page vide).
- Sections affichées : solde de points + **piste « Flow »** (icône par type de cadeau : `tag` bon d'achat, `truck` franco, `percent` BFA — plus de photo de cadeau) (coverflow façon iPod) qui fusionne cadeaux débloqués + cadeau en cours + cadeaux à venir en une seule frise : débloqués (couleur pleine, badge check lime, ordre chronologique) à gauche, cadeau en cours au centre (anneau + halo + badge + mini barre de progression `accent-500`), cadeaux à venir verrouillés (badge `lock`, image conservée en couleur) à droite. Puis liste compacte « Suivi de vos cadeaux débloqués » (statut + date) et historique des points (`points_history`).
- **Piste Flow — implémentation** : composant Alpine `loyaltyFlow` (`resources/js/loyalty-flow.js`, exposé en fabrique globale `window.loyaltyFlow` — même pattern que `pickupMap`, cf. le commentaire du fichier pour la course évitée avec `alpine:init`). Le positionnement n'est **pas** dérivé du scroll natif du navigateur : chaque carte est en `position:absolute`, et un offset virtuel continu (`active`, piloté par molette/drag/tactile) détermine en direct `translateX`/`rotateY`/`opacity` de chaque carte via `cardStyle(index)`. Ce choix permet de faire défiler/pivoter même quand le contenu ne déborde pas nativement, un mouvement continu pendant le drag (pas de saut entre états figés), et une animation de snap (`transition-[transform,opacity]`) qui remet la carte centrée à plat au relâchement. Toutes les cartes latérales partagent la **même taille et le même border-radius** (`rounded-lg`) — seule la rotation varie, jamais l'échelle (sinon effet de « pop » brutal au passage au centre). La bascule est linéaire sur tout l'écart entre deux cartes (`d * -58`, plafonné à ±58°) : l'angle max n'est atteint qu'au moment exact où la carte suivante prend le relais au centre — une rampe qui sature trop tôt fige visuellement la rotation avant la fin du trajet.
- Clés du snapshot : `total_points`, `prev_points` (dernier palier atteint, base de la piste), `next_tier` (LoyaltyTier|null), `upcoming_tiers` (**tous** les prochains LoyaltyTier, triés par points_required), `progress_percent`, `points_to_next`, `unlocked_tiers` (GiftHistory[]), `points_history` (PointsHistory[]), `all_tiers_unlocked`, `no_tiers_configured`.
- Icônes `gift`, `lock`, `trophy` ajoutées au set DS partagé `storefront::components.ui.icon`.
- **Couleur du connecteur de progression** : lime (`accent-500`, vert clair de la charte), jamais `primary`/forest — cf. §3.3 règle 4 (accent lime réservé à un seul élément fort par vue, ici le cadeau en cours de déblocage).
